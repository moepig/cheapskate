# Reconcile の永続化境界

Reconciler は、AWS 操作と DynamoDB への記録を 1 つのトランザクションにはできない。そのため、操作意図と操作結果の順に Status を遷移させ、Lambda が途中で終了しても次回の実行で AWS 操作の結果を確定できるようにしている。通知は Status の遷移に含めない。

## AWS 操作の永続化

リソースごとの操作は、次の順序で進む。

1. `pending_operation_id` が空の場合だけ、操作 ID、所有グループ、および有効設定のハッシュを含む操作意図を記録する。
2. AWS 操作を実行する。
3. 同じ操作 ID を条件に、操作意図を完了記録へ原子的に置き換える。
4. 操作時刻を含む通知を最大 2 回送信する。

AWS 操作の成功後、完了記録より前に処理が終了した場合は `pending_operation_id` が残る。次のサイクルは AWS の観測状態から結果を確定し、同じ AWS 操作を再実行しない。

未完了操作が残っている間にタグ所属または設定が変わった場合も、操作開始時の `pending_group` と `pending_config_hash` を保持する。完了通知は操作開始時のグループへ送り、そのサイクルでは新しい設定に基づく AWS 操作を開始しない。次のサイクルから現在の所有グループと設定を適用する。これらの属性がない旧バージョンの Status は、現在のグループへ帰属させる互換動作で回復する。

## 通知の配送境界

各通知は、同じ処理内で Publish を最大 2 回実行する。2 回とも失敗した場合は送信を打ち切り、Status に再送待ちを残さない。通知の送信失敗は reconcile のエラーとせず、後続する AWS 操作も停止しない。

通知本文の `at` は通知送信時刻ではなく、通知の対象となる操作、エラー、または復旧の時刻である。通知が重複した場合も、2 回の本文は同じ `at` を保持する。異なる通知の到着順が入れ替わった場合は、`at` により前後関係を判定できる。アクション通知の `operation_id` は、同じ操作に対する重複の識別に使用できる。

通知は永続化しないため、完了記録の後から Publish の前までに Lambda が終了した場合は欠落しうる。永続的な再送が必要な場合は、操作 ID をキーにした outbox 項目を追加し、AWS 操作の完了記録と outbox 項目の作成を DynamoDB のトランザクションで確定する必要がある。
