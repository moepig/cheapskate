# Reconcile の永続化境界

Reconciler は、AWS 操作と DynamoDB への記録を 1 つのトランザクションにはできない。そのため、操作意図、操作結果、通知確認の順に Status を遷移させ、Lambda が途中で終了しても次回の実行で処理を継続できるようにしている。

## アクション通知を 1 件だけ保持する理由

各リソースの Status は、アクション通知の再送待ちを `notification_pending` の 1 件だけ保持する。これは通知キューの簡略版ではなく、リソースごとの操作を直列化する不変条件に基づく保存形式である。

処理は、次の順序で進む。

1. `pending_operation_id` と `notification_pending` がともに空の場合だけ、操作意図を記録する。
2. AWS 操作を実行する。
3. 同じ操作 ID を条件に、操作意図を完了記録と `notification_pending` へ原子的に置き換える。
4. 通知を送信し、同じ操作 ID を条件に `notification_pending` を解除する。
5. 解除できるまで、次の AWS 操作を開始しない。

Reconciler はリソースの後続処理より先に未確認通知を再送し、送信または確認記録に失敗した場合は、そのリソースの処理を終了する。DynamoDB の条件式も、未確認通知がある状態での操作開始と通知待ちの上書きを拒否する。このため、正常な状態遷移で 2 件目の未確認通知が発生することはなく、単一スロットで情報を失わない。

この保存形式には、次の利点がある。

- AWS 操作の完了記録と通知待ちへの遷移を、1 つの Status 項目への 1 回の更新で確定できる。
- 通知障害中も項目サイズが増えず、通知順序、削除期限、キューの掃除を別途管理する必要がない。
- 通知の確認が完了していない操作を後続操作が追い越さないため、受信側がリソースの変化を操作順に扱える。

一方、通知先の障害が続く間は、そのリソースに対する新しい AWS 操作も停止する。これは通知を欠落させないための意図した制約である。

`notification_pending` は、厳密には「未送信」ではなく「送信の確認が完了していない」操作 ID である。Publish の成功後、確認記録より前に処理が終了すると、次回は同じ `operation_id` を再送する。そのため、配送保証は at-least-once であり、受信側は `operation_id` を重複判定に利用する。

## 複数件を保持する設計への移行条件

次のいずれかが必要になった場合、単一スロットの不変条件は成立しない。

- 通知障害中も同じリソースへの AWS 操作を続行する。
- 操作通知の履歴を cheapskate 側で保持する。
- 複数の通知先について、確認状態を個別に管理する。

その場合は Status のリスト属性を増やすのではなく、操作 ID をキーにした outbox 項目へ移行する。AWS 操作の完了記録と outbox 項目の作成を DynamoDB のトランザクションで確定し、順序、保持期間、重複排除、削除処理を明示的に設計する必要がある。
