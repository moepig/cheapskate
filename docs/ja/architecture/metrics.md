# メトリクス

## 発行方式

reconciler は `PutMetricData` を呼ばない。EMF(CloudWatch Embedded Metric Format)のログ行を stderr へ出力し、CloudWatch Logs がそれを取り込んでメトリクスを生成する。

この方式では、API 呼び出しに伴うレイテンシ・スロットリング・リトライが増えず、実行ロールに `cloudwatch:PutMetricData` を要さず、Lambda の既存のロググループ以外に作成するリソースが無い。

実装は `internal/aws/cloudwatch` にあり、`internal/app` はメトリクスを知らない。発行は `cmd/reconciler` が `reconcile.Summary` を受け取ってから行う。

## 発行するメトリクス

名前空間は `METRICS_NAMESPACE`(既定 `cheapskate`)、次元は持たず、単位はすべて Count である。発行するメトリクスを、以下に示す。

| メトリクス | 意味 | 発行タイミング |
| --- | --- | --- |
| `ReconciledResources` | そのサイクルで処理したリソース件数 | サイクル完走時のみ |
| `ReconcileActions` | 実行した start/stop の件数 | サイクル完走時のみ |
| `ReconcileErrors` | リソース単位・グループ単位の失敗件数 | サイクル完走時のみ |
| `ReconcileAborted` | サイクル自体が立ち上がらなかったとき `1`、完走したとき `0` | 毎サイクル |

`ReconcileAborted` だけは完走時にも `0` を出す。片側しか出さないとアラームが常にデータ不足に落ち、異常と無音を区別できなくなるためである。

サイクルが中断した場合、残り 3 つのデータポイントは存在しない。処理件数が 0 だったのではなく、数える対象に到達していないためである。

Lambda がタイムアウトまたは panic した場合は、プロセスが落ちるためどのメトリクスも出ない。

## 次元を持たない理由

グループ名を次元にすると、カスタムメトリクスの数がグループ数に比例して増える。cheapskate は本体のコストを月 1 ドル未満に収めることを目標としており、グループ数に比例してメトリクス料金が本体を上回る構成を取らない。

グループ単位の情報は `status#group#<名前>` の `last_error`、SNS 通知の件名、ログの `group` 属性が持つ。メトリクスの役割は異常の発生を検知するところまでであり、発生箇所の特定はそちらが担う。

## Lambda 組み込みメトリクスとの分担

組み込みメトリクスと EMF メトリクスが、それぞれ何を捉えるかを、以下にまとめる。

| メトリクス | 何を捉えるか |
| --- | --- |
| `Errors`(組み込み) | サイクル全体の異常と、リソース単位の失敗が 1 件以上あったサイクル |
| `Duration`(組み込み) | 1 サイクルの所要時間 |
| `Throttles`(組み込み) | 予約同時実行数 1 に対する呼び出しの詰まり |
| `ReconcileErrors` | 失敗の件数。`Errors` は 0/1 しか区別しない |
| `ReconcileActions` | start/stop の発生。恒常的に 0 なら設定が効いていない |
| `ReconciledResources` | 管理下のリソース数の推移 |

`Errors` がリソース単位の失敗も捉えるのは、失敗件数が非零ならハンドラがエラーを返すためである([overview.md](overview.md) の reconcile ループの規則)。

## 失敗の種類と観測箇所

失敗の種類ごとに、どの観測経路へ現れるかを、以下にまとめる。

| 失敗 | `Errors` | `ReconcileErrors` | `ReconcileAborted` | SNS | `status#` | ログ |
| --- | :---: | :---: | :---: | :-: | :---: | :--: |
| Stop/Start の失敗、Describe の失敗 | ✓ | ✓ | 0 | ✓ | ✓ | ✓ |
| 不正な cron / timezone、検出の失敗 | ✓ | ✓ | 0 | ✓ | ✓ | ✓ |
| セレクタの重複 | ✓ | ✓ | 0 | ✓ | ✓ | ✓ |
| payload 不正、`Scan` の失敗 | ✓ | — | 1 | — | — | ✓ |
| Lambda のタイムアウト / panic | ✓ | — | — | — | — | 部分 |
| SNS Publish の失敗、`status#` 書き込みの失敗 | — | — | 0 | — | — | ✓ |
| 遷移中のまま止まったリソース | — | — | 0 | — | ✓(`transitioning_since`) | ✓ |

記録系の失敗と、終わらない遷移をどこにも現れない扱いにしているのは、どちらも操作自体は失敗していないためである。前者はログ([logging.md](logging.md))、後者は診断([overview.md](overview.md))が捉える。

## 無効化

`METRICS_ENABLED=false` で EMF 行そのものを出力しなくなる。

有効・無効(`METRICS_ENABLED`)と名前空間(`METRICS_NAMESPACE`)は別の変数とする。1 つにまとめると「未設定なら既定の名前空間で有効、空文字列なら無効」という約束が必要になり、この変数だけ未設定と空文字列の意味が変わるためである。

`METRICS_ENABLED` が解釈できない値である場合は、既定へ倒さず起動を失敗させる。打ち間違いを有効と解釈すると、無効化したはずの課金が継続し、検知手段が請求のみとなるためである。無効時はコールドスタートごとに `metrics-disabled` のログを 1 行出力する。

有効・無効の判定は `cloudwatch.Emitter` 型自身が持ち、呼び出し側に条件分岐を置かない。発行箇所は複数あり、そのすべてへ同じ条件を記述した場合、一部の記述漏れが生じうるためである。

無効時に失われるのは件数と推移だけである。残るものと失われるものを、以下にまとめる。

| 無効時も残るもの | 無効時に失われるもの |
| --- | --- |
| Lambda 組み込みの `Errors` / `Duration` / `Throttles` | `ReconcileErrors`(失敗の件数) |
| SNS 通知(アクション・失敗・復旧) | `ReconcileActions`(アクションの発生) |
| `status#` の `last_error` | `ReconciledResources`(管理下リソース数の推移) |
| ログ | `ReconcileAborted`(呼び出しが途切れたことの検知) |

リソース単位の失敗が組み込みの `Errors` に乗るため、メトリクスを無効にしても失敗の発生そのものには気づける。

## コスト

EMF で生成されるメトリクスはカスタムメトリクスであり、CloudWatch の課金対象となる。内訳を、以下に示す。

| 項目 | 数 | 概算(東京リージョン) |
| --- | --- | --- |
| カスタムメトリクス | 4 | 約 $0.30/個/月 = 約 $1.20/月 |
| アラーム(標準解像度) | 1〜3 | $0.10/個/月 |
| EMF のログ取り込み | 数行/サイクル | Lambda の既存ロググループ分のみ |

> [!IMPORTANT]
> メトリクスを有効にすると、その費用だけで本体(Lambda + DynamoDB オンデマンド)の月額を上回りうる。本体のコストが月 1 ドル未満であるという記述はコンピュートとストレージについてのものであり、可観測性の費用を含まない。

次元を持たないため、グループやリソースを増やしてもこの 4 メトリクスから増えることはない。

## ローカル実行

ローカル実行時も EMF 行は stderr に出力されるが、取り込む CloudWatch Logs が無いためメトリクスにはならず、JSON ログ 1 行として読める。

`internal/aws/cloudwatch` のテストは `_aws` ブロックの構造そのものを検証する。EMF は形が合っていないと CloudWatch がメトリクスを生成せず、しかもエラーにならず静かに無視されるため、ログが出たことを確かめても意味がないためである。
